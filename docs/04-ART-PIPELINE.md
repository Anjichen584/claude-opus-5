`最后更新: 2026-09-29` `状态: v1.3(规范定稿,资源 96/约96 项 —— **第四批美术清单全部完成**;12 技能图标全专属 + 10 张专属特效)`

## 1. 法务红线(最高优先级)

- 所有美术资源**必须原创生成**,禁止使用/临摹任何现有商业游戏的角色形象、场景素材、UI 皮肤。
- 角色/怪物/地名/技能名不得与《元气骑士》系列雷同。
- 生成资源入库前对照本条自查;有疑义的资源直接废弃重做。

## 2. 风格定义

- **总基调**: 高细节像素风,明快高饱和,描边像素艺术(1px 深色描边 + 内部高光)。
- **分辨率标尺**: 玩家角色 32×32 逻辑像素(渲染放大 3x,最近邻采样,禁止抗锯齿)。
- **调色板**: 全项目统一色板在 `public/assets/palette.png`(`tools/iconize.py --build-palette` 可重建)。
  **实测结论(2026-09-29,`tools/palette_audit.py` 可复跑)**:对**已有**精灵做事后量化是**不可取的** ——

  | 目标色数 | 平均色偏(RGB 欧氏) | 95 分位 | 体积 | 超阈值(>12)的图 |
  |---|---|---|---|---|
  | 64 | 26.8 | 77.3 | 371 KB → 178 KB(-52%) | 76/81 |
  | 128 | 19.4 | 62.5 | 371 KB → 215 KB(-42%) | 66/81 |
  | 256 | 13.7 | 54.7 | 371 KB → 241 KB(-35%) | 41/81 |

  现有精灵是 AI 生成的**高细节伪像素**(单张中位 481 色),压到 256 色仍有可见失真,而省下的
  130 KB 对首屏无意义(精灵是并行加载的图片,JS 主体 222 KB 才是大头)。
  所以规则改成两条:**① 新资源按色板生成(生成阶段对齐,不是事后压缩);
  ② 事后量化只作可选项**(`--apply-palette`,自带 `art_src/_backup` 备份),
  真要压体积请先跑 `palette_audit.py` 看数据再决定。
- **光影**: 光源固定左上 45°;所有实体带 1 张椭圆软阴影(代码绘制,非贴图)。
- **轮廓可读性**: 任何怪物剪影必须在纯黑填充下仍可与其他怪区分(剪影测试)。

## 3. 资源尺寸与动画规格

| 类别 | 画布 | 动画(帧) | 帧率 |
|---|---|---|---|
| 玩家 | 32×32 | 待机4 / 跑6 / 普攻3段各4 / 翻滚5 / 受击2 / 死亡6 | 10fps,攻击 15fps |
| 杂兵 | 24×24~32×32 | 待机4 / 移动4~6 / 攻击4 / 死亡4 | 10fps |
| 精英 | 48×48 | 同上 + 特殊技 6 | 10fps |
| Boss | 96×96 | 待机6 / 三阶段技能各 6-8 / 死亡10 | 12fps |
| 地块 tile | 16×16 | 静态(水面等 4 帧循环) | — |
| 技能特效 | 32~96 | 6-10 帧一次性 | 15fps |
| UI 图标 | 16×16(小)/ 32×32(技能/物品) | 静态 | — |

**序列帧(≥3 帧的动作)规范 · 2026-09-29**:多帧动作走 `tools/process_frames.py`("同画布 + 脚底贴底 + 锚点帧定比例"三条硬口径:
**比例按登记表里人工指定的锚点帧算** —— 按"身体连通域高度"归一会把剑算进身高,挥砍帧整个人会缩错),
文件名 `{类别}_{动作}_{序号}.png`(序号 1 起,如 `knight_walk_1..4`);动作清单与帧数/帧率在 `balance.anim`,
运行时由 `gfx/anim.ts` 解析(缺整套序列自动降级,见该文件头注释)。**别用 `process_art.py` 的单图分支处理序列帧** ——
那套按"主体 bbox 缩放到目标高"逐帧缩放,抬手/剑尖上挑的那一帧会被缩得跟别的帧不一样大(双帧时代踩过的坑,序列帧是同一个坑)。

**两帧资产与序列并存(2026-09-29 定)**:杂兵/中Boss 早期只有两张图,命名 `{base}` + `{base}_f2`;
玩家/精英走序列 `{base}_{action}_{i}`。两套**并存不合并**(图鉴里 22 只怪都是 `_f2`,重命名收益为零、风险不小),
运行时由 `anim.ts` 的 `twoFrame()` 统一处理,取舍就是:**节奏只有一个来源**。
两帧资产的翻帧步长**推导**自 `balance.anim.walk`(走路一圈 = 两个步幅 → 每半圈翻一次 = 每两个走路帧翻一次,
即 `frames/fps/2` 秒);别在渲染层手写 `floor(t*8)%2` —— 那个数当时比玩家走路快一倍,
而且改帧率时玩家会变、杂兵不会(现在两端都只有这一个来源,Unity 侧是 `AnimRules.TwoFrameFlip`)。

> **体积政策(2026-09-29 定)**:`web/art_src/` 的源图**不进仓库**(`.gitignore` 已挡)。
> 源图 ~80 MB、成品精灵 ~0.5 MB —— 源图入库会在 128 MB 的构建沙箱里触发快照裁剪,
> 导致大文件被静默丢弃(已发生过一次)。可再生性由两件事保证:成品精灵留在仓库、
> 生成提示词存 `docs/08-ART-PROMPTS.md`。改图流程见 `web/art_src/README.md`。

## 4. 生成与入库流程(AI 生成 → 规范化 → 图集)

> **抠图坑位(踩过,记牢)**:品红幕布必须按**通道**判定(`R>165 且 B>165 且 G<110`),
> 不能按"通道和距"——白/浅蓝精灵与品红只差 G 通道,用 sum-abs 会把雪绒球这类白色生物整只吃掉。
> 绿幕保留 sum-abs 判定(护住绿色生物)。
>
> **双帧动画坑位**:两帧裁剪必须按**主体连通域**(最大域 + 面积≥5% 的部件)缩放与对齐,
> 不能按全图 bbox——带落叶/沙尘/雪粉的帧 bbox 会变宽变高,底锚绘制时身体会跳、还会一大一小。
> 实现见 `tools/process_art.py` 的 `PAIRS` / `process_pair()`。

1. 按 §2 风格 + §3 尺寸生成候选图(生成 prompt 存 `webassets-src/prompts.md` 备查);
2. 人工筛选 → 缩放到目标逻辑像素 → 锁 64 色板(脚本 `web/tools/quantize.ts`,Phase 1 建);
3. 逐帧拼 spritesheet(横排),命名 `{类别}_{id}_{动作}.png`,如 `enemy_shroomling_walk.png`;
   多帧动作走 `tools/process_frames.py`(登记到该文件的 `SEQUENCES`,输出 `{类别}_{动作}_{序号}.png`);
4. 运行 `web/tools/pack-atlas.ts` 生成图集 PNG+JSON 到 `public/assets/sprites/`;
5. 在 §6 资源清单打勾并填 commit。

## §9 位图数字字体(第四批美术 · 2026-09-29)

**为什么字体不进"AI 生成精灵"流程**:字模对形状的容错是 0 —— 一个像素错位就是另一个字。
所以数字字体不走图像生成,而是**手写位图字模 + 双端同源数据**:

- 权威数据:`web/src/data/font.json`(5×7、字距 1、24 个字符:0-9 / `.` `:` `/` `-` `+` `x` `,` `%` / 空格 / `P F S K H`)。
- web 渲染:`web/src/game/gfx/pixelFont.ts` —— 每个点亮像素画一个 `scale×scale` 的 `fillRect`,
  坐标与缩放全部取整,所以任何位置/任何倍数下都不会出现半个像素的毛边;
  描边分两趟(先摊 `3×scale` 的边框块、再落本体块,共 `2N` 个方块,N = 点亮像素数),
  而不是"8 邻域各画一遍"的 `9N` —— 帧内飘字最多时这点开销是能看出来的。
- Unity 镜像:`unity/Assets/Scripts/Core/PixelFont.cs`(同一份字模),`ParityTests` **逐字符逐行**比对,
  改一边忘另一边立刻红(实测抹掉 `0` 的一行斜杠 → 3 条断言报红)。
- 边界:**中文不进位图字模**(5×7 塞不下),整串含中文时整串回退平台字体,不做中英混排
  —— 混排的像素比例对不上,反而更难看。调用方用 `supports(text)` 判断。

| 接入点 | 之前 | 现在 |
|---|---|---|
| 伤害飘字 | canvas `13px monospace` + strokeText | 像素字体,1/2/3 倍分档 + 1px 像素描边 |
| 血量数字 | `11px monospace` | 像素字体(低血变红) |
| 击杀 / FPS | 一行中文混排 | 中文标签走平台字体、数字走像素字体,分开画 |
| 技能冷却秒数 | `13px monospace` | 像素字体 ×2 |

## §10 图标管线与"回炉通道"(第五批美术 · 2026-09-29)

**为什么单独一条管线**:图标是**小尺寸、强约束**资源(24px 高、要能塞进背包格、剪影要认得出),
用主流程 `process_art.py` 的"按固定目标高降采样"会得到参差不齐的宽度(实测武器 8px 宽、靴子 28px 宽),
塞进 56px 的格子里视觉重量差很多。做法:

- `tools/iconize.py` 的 `ICON_TARGETS` 统一登记图标目标高:物品/状态 24、技能 30;
- 抠幕布**复用 `process_art.key_out`**(不复制实现,避免两份逻辑漂移 —— 品红按通道判、绿幕按色距判的坑只保留一处);
- 成品入库后**立刻删除源图**(本轮 10 张源图 10 MB → 0),可再生性靠 `docs/08-ART-PROMPTS.md` 的提示词存档;
- 接线点与回退:`gfx/icons.ts` 的 `ITEM_ICON`(按 `Slot`)/ `STAT_ICON`(按语义键)+ `drawIcon` /`drawIconRow`,
  **未加载返回 false**,调用方回退到原程序化画法(稀有度外框、字形)——所以缺图只会视觉降级;
- 已接入:背包与装备位(6 部位图标)、结算页统计行(击杀/受击/最高伤害/推进+用时,图标 + 左对齐文字)。

**为什么结算页要顺带加两行**:排行榜的数据源(`FeedbackSystem.hitsTaken` / `maxHit`)本来就在跑,
但只在榜单里可见;把"受击 N 次(无伤!)"和"最高单次伤害"放到结算页,玩家立刻知道这两个数是怎么来的。
